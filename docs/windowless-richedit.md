# 无窗口 RichEdit 工作原理

> 本文是 balloonui 富文本控件 `DuiRichEdit` 的原理说明，最初写在代码之前。
>
> 它**不是**接口手册。想知道某个方法怎么调，去看 `DuiRichEdit.h` 的注释；
> 想知道这个控件为什么长成这样、出问题时该从哪儿查起，看本文。
>
> 状态：**控件已实现**（2026-08-15）。写作时的绝大部分推测已在实现过程中验证，
> 结论连同新发现的坑一并汇总在第 11 节。仍未验证的只剩两项，见 11.2，都已列入
> 人工核对清单。
>
> **关于文中与 `DuiRichEditHost` 的对比。** 本文成文时，库里还并存着另一个走真
> 子窗口路线的富文本控件 `DuiRichEditHost`。该控件此后已整体删除，全部调用方
> （PC 客户端的聊天窗与升级窗、flamingoAdmin 的公告面板等）均已改用
> `DuiRichEdit`，XML 标签也由 `<richedit>` 统一为 `<richtext>`。文中凡是拿两者
> 作对比的段落，一律按回顾来读：它们记录的是当初为什么要另起一个无窗口控件，
> **不表示今天还有两条路线可供选择**。

## 1. 这份文档要解决的问题

Windows 的 RichEdit 是一个**闭源**的文字排版引擎，随系统提供。它有两种用法：

- **真窗口用法**：用 `CreateWindowEx` 建一个窗口类为 `RICHEDIT50W` 的子窗口，
  之后一切都是它自己的事——它有自己的窗口句柄、自己收消息、自己画、自己管光标和输入法。
  balloonui 早先的 `DuiRichEditHost` 走的就是这条路，该控件现已删除。
- **无窗口用法**：不建窗口，只向系统要一个排版引擎对象，然后**由我们自己**告诉它
  "客户区多大""现在该画到这个设备上下文里""用户按了这个键"，同时**由我们自己**响应它
  提出的各种要求——"给我一个设备上下文""帮我把光标挪到这里""帮我显示滚动条"。
  `DuiRichEdit` 走的是这条路，也是库内目前唯一的富文本实现。

第二条路难在哪里？难在**主动权是反的**。写普通控件时，代码是自己在跑，需要什么就去调什么；
写无窗口 RichEdit 时，真正在跑的是那个闭源引擎，我们写的绝大部分函数都是**被它回调**的。
每个函数都很短，但"引擎为什么在这个时候问这个问题""我们答错了会发生什么"，光看代码是看不出来的。

所以这份文档的核心内容只有一件事：**把这层控制反转关系讲清楚**。讲清楚之后，
四十来个短函数就不再是四十个黑箱，而是一张能读懂的问答表。

## 2. 责任分工：两种模式各自谁在干活

同一件事，两种模式下由不同的一方负责。这张表是理解一切的基础：左列是已删除的真窗口
控件当年的做法，列在这里不是为了比较优劣，而是为了说清无窗口模式下多出来的那些责任
究竟从哪里来。

| 事情 | 真窗口模式（已删除的 `DuiRichEditHost`） | 无窗口模式（`DuiRichEdit`） |
| --- | --- | --- |
| 排版、断行、字形绘制 | 引擎 | 引擎 |
| 撤销栈、选区、查找 | 引擎 | 引擎 |
| 提供绘制目标 | 引擎自己向系统要 | **我们提供** |
| 决定什么时候画 | 系统的绘制消息 | **我们在自己的绘制函数里调引擎** |
| 接收鼠标键盘消息 | 系统直接送给它的窗口 | **我们收到后转发给引擎** |
| 光标的创建、显示、定位 | 引擎自己做 | **我们做**，引擎只告诉我们位置 |
| 滚动条的显示、范围、位置 | 引擎自己做 | **我们做**，引擎只告诉我们参数 |
| 输入法上下文 | 引擎自己向系统要 | **我们提供**（来自宿主窗口） |
| 鼠标捕获、键盘焦点 | 系统的窗口机制 | **我们用 DUI 树的对应机制模拟** |
| 定时器 | 引擎自己向系统要 | **我们提供**，到点后通知引擎 |
| 客户区大小、内边距 | 引擎从自己的窗口读 | **我们告诉它** |
| 默认字体、默认段落格式 | 引擎从窗口的字体读 | **我们告诉它** |
| 只读、多行、密码等属性 | 编码在窗口风格位里，创建后固定 | **我们随时可答**，因此运行期可改 |

最后一行是当初决定另起一个无窗口控件的一条实在理由：真窗口控件要把多行改成单行，
只能销毁子窗口再重建；`DuiRichEdit` 只是改一个成员变量，再通知引擎一声。

## 3. 控制反转：两个接口，两个方向

引擎和我们之间隔着两个接口，方向正好相反。**分清这两个方向，后面就不会乱。**

```
                 ┌──────────────────────────────┐
                 │        DuiRichEdit           │  ← 我们写的控件
                 │  （DuiControl 的子类）        │
                 └───────┬──────────────▲───────┘
                         │              │
       我们主动调引擎  ↓ │              │ ↑  引擎主动回调我们
       ITextServices     │              │    ITextHost
       （18 个方法）      │              │    （39 个方法）
                         │              │  ← 这一侧由 DuiTextHost 实现
                 ┌───────▼──────────────┴───────┐
                 │   系统里的 RichEdit 排版引擎   │  ← 闭源，msftedit.dll
                 └──────────────────────────────┘
```

- **`ITextServices` 是引擎实现的**，我们拿到它的指针，需要什么就调它。
  典型场景：绘制时调它画、收到按键时调它处理、要读文本时调它给。
- **`ITextHost` 是我们实现的**，我们把自己的对象指针交给引擎，引擎需要什么就回调我们。
  典型场景：它要量文字时问我们要设备上下文、它算出光标该在哪儿了让我们挪过去。

两者在对象创建时一次性接上：我们向系统的 `CreateTextServices` 函数递上自己的
`ITextHost` 实现，它还回来一个 `ITextServices`。此后两个方向同时存在，
**一次用户操作往往两个方向来回好几趟**——这是最容易绕晕的地方，第 8 节会逐步拆开。

在 balloonui 里，`ITextHost` 的实现是单独一个类 `DuiTextHost`，而不是让
`DuiRichEdit` 自己去继承。这样分是有意的，理由有三条：

1. `ITextHost` 是 COM 接口，带引用计数，生命周期由引擎决定；`DuiControl` 的生命周期
   由 DUI 树决定。两套生命周期规则揉进一个类里，早晚会出现"控件已经析构了引擎还在回调"
   这类问题。拆开之后，`DuiTextHost` 可以在引擎放手之后才真正销毁。
2. 39 个方法混进控件类里，会把控件本身的代码淹掉。
3. 这 39 个方法有很强的共性——绝大多数是"把引擎的请求翻译成 balloonui 的能力"，
   放在一个文件里能统一注释风格，也便于对照本文档阅读。

### 3.1 两个接口标识符必须自己声明

据实证（参考实现 `SRichEdit.cpp:169-183`）：`IID_ITextServices` 与 `IID_ITextHost`
**没有任何导入库导出**，必须在自己的代码里用 `EXTERN_C const IID` 手工写死。
这一步漏了会在链接期报"找不到符号"，而不是编译期，容易一时找不到头绪。

## 4. 接口全景

### 4.1 `ITextServices` —— 我们调引擎的 18 个方法

出处：`Windows Kits\10\Include\10.0.22621.0\um\TextServ.h:176-283`。按用途分五组：

**（一）通用消息通道 —— 一个方法顶一大片**

| 方法 | 用途 |
| --- | --- |
| `TxSendMessage(msg, wparam, lparam, plresult)` | 把任意窗口消息交给引擎处理 |

这是最重要的一个方法。真窗口模式下所有发给 RichEdit 窗口的消息——鼠标、键盘、
输入法，以及全部 `EM_` 开头的编辑命令——在无窗口模式下统统改由这个方法送进去。
换句话说，**真窗口控件里所有 `SendMessage(hwnd, EM_XXX, ...)` 的写法，
在 `DuiRichEdit` 里都变成 `TxSendMessage(EM_XXX, ...)`**，参数含义完全一致。
两个控件的接口当初能够保持一致、调用方迁移过来时改动很小，根本原因就在这里。

**（二）绘制与命中**

| 方法 | 用途 |
| --- | --- |
| `TxDraw(...)` | 把文档画到指定的设备上下文上 |
| `OnTxSetCursor(...)` | 告诉引擎鼠标在某坐标上，由它决定光标形状 |
| `TxQueryHitPoint(...)` | 问某个坐标是否命中文字，返回四档结果 |

命中结果有四档（`TextServ.h:53-58`）：没命中、落在文字矩形内但属于透明区域、
接近文字、正中文字。第二档对我们有用——将来做"点击空白处穿透到下层控件"时会用到。

**（三）滚动状态查询**

| 方法 | 用途 |
| --- | --- |
| `TxGetHScroll(plMin, plMax, plPos, plPage, pfEnabled)` | 取水平滚动的范围、当前位置、可视页大小、是否启用 |
| `TxGetVScroll(...)` | 同上，垂直方向 |

注意这是**查询**，不是设置。设置的方向是反的：引擎通过 `ITextHost` 让我们去摆滚动条。
我们主动查询的场合是"用户拖了滚动条，我们需要知道引擎现在认为滚到哪儿了"——
这一步不能省，原因见第 5.3 节。

**（四）激活状态**

| 方法 | 用途 |
| --- | --- |
| `OnTxInPlaceActivate(prcClient)` | 就地激活：告诉引擎"你开始工作吧" |
| `OnTxInPlaceDeactivate()` | 就地反激活：控件销毁前调用 |
| `OnTxUIActivate()` | 界面激活：本控件拿到了键盘焦点 |
| `OnTxUIDeactivate()` | 界面反激活：本控件失去了键盘焦点 |

两对四个方法，容易混。区别是：**就地激活**关心的是"这个引擎实例有没有在干活"，
控件创建时激活一次、销毁时反激活一次；**界面激活**关心的是"用户现在是不是在跟我交互"，
每次焦点进出都要切换一次。光标闪不闪、选区高亮不高亮，取决于后者。

**（五）内容读写与测量**

| 方法 | 用途 |
| --- | --- |
| `TxGetText(pbstrText)` / `TxSetText(pszText)` | 读写全文纯文本 |
| `TxGetNaturalSize(...)` | **测量内容的自然尺寸** |
| `TxGetCachedSize(pdwWidth, pdwHeight)` | 取上一次排版缓存下来的尺寸，比重新测量快 |
| `TxGetCurTargetX(plong)` / `TxGetBaseLinePos(plong)` | 取当前目标横坐标 / 基线位置 |
| `TxGetDropTarget(ppDropTarget)` | **要一个拖放目标对象** |
| `OnTxPropertyBitsChange(dwMask, dwBits)` | 通知引擎"某些属性变了" |

其中两个是本控件的关键能力来源：

- `TxGetNaturalSize` 配合 `TXTNS_FITTOCONTENT`（`TextServ.h:68-79`）能算出
  "刚好装下当前内容需要多大"。把它接到 balloonui 布局体系的期望尺寸接口
  （`DuiControl::GetDesiredSize`）上，就得到了**随内容自动增高的输入框**。
  真窗口控件做不到这一点，因为它拿不到引擎内部的排版结果。
- `TxGetDropTarget` 直接把一个符合系统拖放规范的目标对象交给我们，注册上去即可。
  **拖放几乎是白送的**，不需要自己解析拖放数据。

### 4.2 `ITextHost` —— 引擎回调我们的 39 个方法

出处：`TextServ.h:317-445`。按"我们要付出多少工作量"分四档，这个分法比按功能分更实用：

**A 档：直接返回成员变量或常量即可（19 个）**

`TxGetSysColor`、`TxGetBackStyle`、`TxGetMaxLength`、`TxGetScrollBars`、
`TxGetPasswordChar`、`TxGetAcceleratorPos`、`TxGetExtent`、`TxGetSelectionBarWidth`、
`TxGetCharFormat`、`TxGetParaFormat`、`TxGetPropertyBits`、`TxGetClientRect`、
`TxGetViewInset`、`TxActivate`、`TxDeactivate`、`OnTxCharFormatChange`、
`OnTxParaFormatChange`、`TxGetDC`、`TxReleaseDC`。

这一档占了将近一半。它们的实现往往只有一两行，但**注释必须写足**——
因为"返回什么"很简单，"为什么返回这个、单位是什么、坐标系是哪套"才是全部信息量所在。

其中三个可以直接返回常量，省力：`TxGetSelectionBarWidth` 返 0（关掉左侧整行选择条）、
`TxGetAcceleratorPos` 返 -1（没有助记符）、`OnTxCharFormatChange` 与
`OnTxParaFormatChange` 直接返回成功。

**B 档：转发给 balloonui 现成能力（10 个）** —— 详细映射见第 9 节。

**C 档：balloonui 现在没有，必须新写（5 个）**

| 引擎的要求 | 现状 |
| --- | --- |
| `TxCreateCaret` / `TxShowCaret` / `TxSetCaretPos` | balloonui 全库没有任何光标代码，新写 `DuiCaret` |
| `TxImmGetContext` / `TxImmReleaseContext` | balloonui 全库没有任何输入法代码，需要宿主配合 |

**D 档：可以简化处理（2 个）**

| 引擎的要求 | 我们的做法 |
| --- | --- |
| `TxSetTimer` / `TxKillTimer` | 用宿主窗口的系统定时器，到点后转发给引擎 |
| `TxScrollWindowEx` | 引擎希望我们做位块搬移以加速滚动；直接整块失效重画即可，正确性不受影响，只是少了一点优化 |

**剩下 3 个是引用计数**（`QueryInterface` / `AddRef` / `Release`），照标准写法即可。
注意一点：引擎会持有我们的引用，所以**控件析构时不能直接 `delete` 这个对象**，
只能减引用；真正的销毁要等引擎也放手。这正是第 3 节把它拆成独立类的第一条理由。

## 5. 坐标系与单位：本控件最大的认知负担

写这类代码最容易出的错，不是逻辑错，而是**把像素当成了另一种单位、把这套坐标当成了另一套**。
两个相邻的方法要的东西可能完全不同。先把规则立在这里，后面每个涉及坐标或单位的方法注释里
都会点明它属于哪一类。

### 5.1 两种单位

| 单位 | 含义 | 哪里用 |
| --- | --- | --- |
| **像素** | 设备像素 | 绝大多数方法 |
| **HIMETRIC** | 百分之一毫米 | 只有 `TxGetExtent`、`TxGetViewInset` 两个方法 |
| **twip** | 一英寸的一千四百四十分之一 | 字符格式里的字号、段落格式里的制表位 |

换算要经过设备的每英寸点数，公式是固定的：

```
HIMETRIC = 像素 × 2540 ÷ 每英寸点数        （2540 = 一英寸的百分之毫米数）
像素     = HIMETRIC × 每英寸点数 ÷ 2540
twip     = 磅值 × 1440 ÷ 每英寸点数
```

每英寸点数要用 `GetDeviceCaps(hdc, LOGPIXELSX/Y)` 现取，不能写死 96。

**最容易踩的坑在这里**：`TxGetClientRect` 要的是**像素**，而紧挨着的 `TxGetViewInset`
要的是 **HIMETRIC**。两个方法名字像、位置挨着、都返回矩形，单位却不一样。
搞混的症状是文字内边距大得离谱或者干脆是负的，而且因为两者都"看起来能跑"，
不会崩溃也不会报错，只能靠眼睛发现。

参考实现里全仓库只有两个换算函数、调用点集中在一处（`SRichEdit.cpp:186-195`、
`:1314-1320`），我们照此办理：**换算只在一个地方发生，别处一律像素**。

### 5.2 三套坐标系

| 坐标系 | 原点在哪 | 哪里用 |
| --- | --- | --- |
| **控件坐标** | 控件自己的左上角 | 不直接用于引擎交互 |
| **宿主客户区坐标** | 宿主窗口客户区的左上角 | balloonui 的控件矩形、鼠标事件、绘制 |
| **屏幕坐标** | 主显示器左上角 | 弹出菜单、`TxScreenToClient` / `TxClientToScreen` 的参数 |

balloonui 的控件矩形（`m_rcItem`）用的是**宿主客户区坐标**（据实证
`DuiControl.h:195` 的注释）。我们把这套坐标交给引擎，于是引擎回传的一切坐标
——失效矩形、光标位置、命中测试——也都是这一套，前后一致，不需要额外偏移。

**但坐标转换那两个方法是例外，必须小心。** 参考实现在这里有一处潜在缺陷：
它的坐标转换直接拿宿主窗口做换算，没有加上容器自身的偏移，因此控件嵌在列表项
之类的二级容器里时会算错（`SRichEdit.cpp:287-295`，对比 `:1174-1177` 处正确的写法）。
balloonui 里控件矩形本来就是宿主客户区坐标，这个偏移天然为零，**但如果将来出现
嵌套的绘制容器，这里就要补偏移**。实现时在注释里写明这条前提。

**光标定位是最典型的坐标使用点。** 漏了坐标换算的症状是光标永远出现在控件左上角
附近的错误位置，且文字越靠右下偏得越远。

### 5.3 一个与坐标无关、但同样容易错的地方：滚动位置要回读

据实证（参考实现 `SRichEdit.cpp:787-796`）：把滚动位置交给引擎之后，**必须再从引擎
读回真实位置并同步给滚动条**。因为引擎会按行边界对齐，"滚 40 个像素"到它那里可能变成
"滚两行 = 36 个像素"。不回读的症状是滚动条滑块与内容逐渐错位，滚得越多偏得越远。

## 6. 属性位：运行期可改属性的实现机制

真窗口模式下，"多行""只读""密码""自动换行"这些是窗口风格位，写死在创建那一刻。
无窗口模式下，它们变成一组**属性位**，引擎通过 `TxGetPropertyBits` 回来问，
我们从成员变量拼出答案。这就是本控件能在运行期改属性的全部原因。

改属性的完整流程是两步，缺一不可：

1. 改我们自己的成员变量；
2. 调 `OnTxPropertyBitsChange(掩码, 新值)` 通知引擎"这几位变了"。

只做第一步的症状是**改了没反应**——引擎不会主动来问，它只在被通知时才重新读。

常用属性位（出处 `TextServ.h:125-163`）：

| 属性位 | 含义 | 对应我们的哪个开关 |
| --- | --- | --- |
| `TXTBIT_RICHTEXT` | 富文本模式，关掉就退化成纯文本 | 是否允许字符格式 |
| `TXTBIT_MULTILINE` | 多行 | `SetMultiLine` |
| `TXTBIT_READONLY` | 只读 | `SetReadOnly` |
| `TXTBIT_WORDWRAP` | 自动换行 | `SetWordWrap` |
| `TXTBIT_USEPASSWORD` | 用密码字符显示 | `SetPasswordChar` |
| `TXTBIT_HIDESELECTION` | 失焦时隐藏选区高亮 | 内部使用 |
| `TXTBIT_VERTICAL` | 竖排文字 | `SetVertical` |
| `TXTBIT_DISABLEDRAG` | 禁止拖放 | `SetDragDropEnabled` 的反面 |
| `TXTBIT_AUTOWORDSEL` | 双击选词时按整词扩展 | 内部默认开启 |
| `TXTBIT_ALLOWBEEP` | 到达长度上限时是否响铃 | 内部默认关闭 |

另有一组是**通知型**的，不表示状态，只用来告诉引擎"某样东西变了，请重新读"：
`TXTBIT_CLIENTRECTCHANGE`（客户区变了）、`TXTBIT_EXTENTCHANGE`（范围变了）、
`TXTBIT_CHARFORMATCHANGE`（默认字符格式变了）、`TXTBIT_PARAFORMATCHANGE`（默认段落格式变了）、
`TXTBIT_VIEWINSETCHANGE`（内边距变了）、`TXTBIT_BACKSTYLECHANGE`（背景样式变了）、
`TXTBIT_SCROLLBARCHANGE`（滚动条配置变了）、`TXTBIT_MAXLENGTHCHANGE`（长度上限变了）。

**控件尺寸变化时必须发前两个**，否则引擎会按旧尺寸排版——这是重排的命脉
（参考实现 `SRichEdit.cpp:1332`）。

## 7. 背景透明：不是技巧，是引擎的正式支持

`TxGetBackStyle` 的返回值有两档（`TextServ.h:42-45`）：

- `TXTBACK_OPAQUE`：引擎自己擦背景。
- `TXTBACK_TRANSPARENT`：引擎不擦背景，让下面的内容透出来。

选第二档，再由我们在调 `TxDraw` 之前自己把背景画好，就能实现圆角、渐变、
半透明、与父容器卡片底融合等各种效果。**这不是绕过限制的技巧，是接口的正式用法。**
真窗口控件做不到这一点，因为子窗口是独立的绘制单元，父窗口画的东西到不了它下面。

代价是：选了透明，引擎就再也不管背景了，**我们必须每次绘制都自己把背景铺满**，
漏了就会看到上一帧的残留。

## 8. 三条完整调用链路

> **本节整体标注为「据推测」。** 下面的顺序是依据两条证据推导出来的：一是 SDK 头文件
> 定义的接口语义，二是参考实现 SOUI 里实证追踪出来的调用链（`SRichEdit.cpp` 各处）。
>
> 控件实现完成之后（2026-08-15），这三条链路在**行为上**都已成立：打字、绘制、
> 滚动都正常工作。但**具体的回调顺序**仍未逐条核对过，所以本节维持「据推测」。
> 验证方式：在 `DuiTextHost` 的每个方法入口打一条临时日志，跑演示页，记录真实顺序，
> 然后回来把本节改成「据实证」并附上日志片段。库内已有现成的埋点工具，设环境变量
> `BUI_DUI_TRACE=1` 即可打开（见 `DuiTrace.h`）。

### 8.1 用户按下一个字符键

```
 1. 系统把「字符输入」消息投递给宿主窗口
 2. 宿主窗口的消息映射命中 → 交给当前的 DUI 焦点控件
 3. DuiRichEdit 覆写的字符处理函数拿到它
      先做过滤：回车是发送还是换行？Tab 是切焦点还是插制表符？
 4. 过滤后交给引擎：TxSendMessage(字符消息, ...)
      引擎的返回值能告诉我们它有没有处理（详见第 11 节的待验证项）
 5. 引擎内部插入字符、重新排版
 6. 引擎回头调我们（顺序据推测）：
      TxInvalidateRect 或 TxViewChange  —— 要求重画
      TxSetCaretPos                     —— 光标挪到新位置
      TxShowCaret                       —— 确保光标可见
      行数变化时还会调滚动条那一组
      内容变化通知打开时调 TxNotify
 7. 我们在 TxInvalidateRect 里调 balloonui 的失效接口
 8. 宿主窗口下一轮收到绘制消息 → 进入 8.2
```

### 8.2 一次绘制

```
 1. 系统投递绘制消息给宿主窗口
 2. 宿主准备好后台缓冲（一张 32 位位图），先铺整窗背景
 3. 宿主递归调用控件树的绘制函数，把后台缓冲的设备上下文传下来
 4. DuiRichEdit 的绘制函数：
      a. 自己铺背景 —— 因为我们对引擎答的是「背景透明」，它不管背景
      b. 保存设备上下文状态，设裁剪区
         ★ 这一步不能省：balloonui 的宿主与基类都不设裁剪区，
           引擎会按自己的排版结果画，不裁就会画出控件边界
      c. TxDraw(..., 控件矩形, ...)
      d. 恢复设备上下文状态
      e. 最后画滚动条子控件 —— 覆盖式摆放，必须最后画才能盖在文字上
 5. 回到宿主，把后台缓冲整块复制到窗口上
```

### 8.3 一次滚轮滚动

```
 1. 系统投递滚轮消息给宿主窗口
 2. 宿主做命中测试找到控件（滚轮不看焦点，只看鼠标在谁身上），
    控件不消费时沿父链向上冒泡
 3. DuiRichEdit 的滚轮处理函数交给引擎
 4. 引擎回调 TxSetScrollPos 要求我们更新滚动条
      ★ 此处必须有防递归标志，否则会形成无限循环，见第 10.3 节
 5. 我们把引擎的真实滚动位置回读一次再同步给滚动条（见 5.3 节）
 6. 引擎回调 TxInvalidateRect → 进入 8.2
```

## 9. balloonui 侧的落地映射

第 4.2 节的 B 档十个方法，逐个对应到 balloonui 现成的能力。以下 API 均已核实存在。

| 引擎的要求 | balloonui 对应 | 备注 |
| --- | --- | --- |
| `TxInvalidateRect(带矩形)` | `DuiHost::InvalidateDuiRect(rc)` | 公开方法，可局部失效，光标闪烁走这条更省 |
| `TxInvalidateRect(NULL)` / `TxViewChange` | `DuiControl::Invalidate()` | 只能整控件失效，不带矩形 |
| `TxSetCapture` | `DuiControl::Capture()` / `ReleaseCapture()` | 已镜像到系统捕获，拖选出界仍收得到鼠标 |
| `TxSetFocus` | `DuiControl::SetFocus()` | 转调宿主的焦点管理 |
| `TxSetCursor` | 直接调系统设置鼠标指针 | 无需经过 balloonui |
| `TxScreenToClient` / `TxClientToScreen` | 宿主窗口的坐标换算 | 宿主窗口句柄取自 `GetHost()->m_hWnd` |
| `TxShowScrollBar` / `TxEnableScrollBar` / `TxSetScrollRange` / `TxSetScrollPos` | 两个 `DuiScrollBar` 子控件 | 详见 10.3 |
| `TxGetCharFormat` 的字体来源 | `DuiResMgr::Inst().GetDefaultFont()` 等 | 返回裸字体句柄，**所有权在资源管理器，不要销毁**；按字号取字体的接口内部已按屏幕缩放处理 |
| `TxNotify` | `DuiControl::NotifyParent(通知码, 附加值)` | 通知码从 `DUIN_CUSTOM` 起算 |
| `TxGetClientRect` | 控件矩形 `m_rcItem` 减去内边距 | 宿主客户区坐标、像素 |

**两处需要注意的既有情况：**

- 双击：宿主的两个窗口类 `__DuiHost__` 与 `__DuiFrameWindow__` 都带 `CS_DBLCLKS`，
  系统会直接投递 `WM_LBUTTONDBLCLK`，经 `DuiHost::OnLButtonDblClk` 转给控件，本控件
  再把它转给排版引擎（`DuiRichEdit::OnLButtonDblClk`），不需要额外设置。
  （2026-10-06 更正：初稿写的是「宿主窗口类没有注册双击，必须调宿主的
  `EnableDoubleClick(true)` 打开双击合成」，与实际不符。`EnableDoubleClick` 只对
  窗口类不带 `CS_DBLCLKS` 的宿主有意义，见 `DuiHost.h`。）
- 自定义通知码是**按控件各自编号**的，不同控件的第一个自定义码数值必然相同。
  因此本控件应当另开取值段，避开其它控件已占用的编号；派发端也必须把控件编号
  与通知码写在同一个分支条件里，否则排在前面、通知码相同的分支会把本控件的
  通知截走。

### 9.1 布局的「自动档」：自动增高在布局体系里的落脚点

自动增高要生效，布局体系必须支持一种新的尺寸模式。原先的布局提示只有两档：

| 档位 | 含义 |
| --- | --- |
| 固定像素（取值 ≥ 0） | 主轴上占指定的像素数，不参与剩余空间的分配 |
| 按权重（取值 −1） | 不预先占位，等固定档都排完之后，按权重瓜分剩下的空间 |

两档都表达不了「高度随内容变化」：固定像素做不到（内容一变就不对），按权重也做不到
（权重分的是剩余空间，与内容多少无关）。所以加了第三档：

| 档位 | 含义 |
| --- | --- |
| **自动（取值 −2）** | 主轴上占用子控件自己报告的期望尺寸，同样不参与剩余空间的分配 |

**自动档在实现上与固定档归为一类，而不是与按权重归为一类。** 理由是布局分两趟走：
第一趟把「不参与瓜分」的那些子控件的尺寸先减掉，第二趟才让带权重的去分剩下的。
自动档的尺寸在第一趟就能问出来（直接问子控件），所以它属于第一趟那一批。

这里有一个**极易写错的地方**：判断「是不是按权重」不能只写「取值小于 0」——
自动档的取值也是负数，会被一起误判进去。症状是自动档的控件不按内容占位，反而跑去
瓜分剩余空间。库内把这个判断收敛到一个辅助函数里，六处读取点全部走它。

两点使用上的注意：

- 子控件必须**真的覆写了「报告期望尺寸」那个虚函数**。没覆写的默认返回零，
  自动档就退化成「占 0 像素」，控件在界面上完全看不见。
- 交叉轴尺寸在第一趟是未知的，所以**「高度取决于宽度」的控件会慢一帧**。
  富文本正是这种控件，处理办法见 11.1 里「布局第一趟量不出高度」那一条。

## 10. 必须新写的三样东西

### 10.1 光标

balloonui 全库没有任何光标代码——在此之前，库里能编辑文本的两个控件（单行编辑框，
以及当时还在的真窗口富文本控件）都寄宿真子窗口，光标由系统绘制。
所以要新写一个 `DuiCaret`，把系统的光标接口包起来，作用在宿主窗口上。

**这里有一条关键情报，不看参考实现是想不到的：** 参考实现虽然自己画光标，
但它**同时还建了一个真的系统光标，建完立刻隐藏**（`shostwnd.cpp:836-837`）。
目的不是显示，而是**给输入法定位候选窗**——它全仓库都没有调用过设置组字窗位置的接口，
系统只能靠系统光标的位置决定候选条弹在哪儿。据推测，只画自绘光标而不建系统光标，
中文输入时候选条会跑到窗口左上角。

我们选的就是系统光标方案，因此顺带把候选窗定位也解决了。

**2026-09-30 修订：改为与参考实现相同的「自己画光标 + 系统光标只报告位置」。**
直接显示系统光标在实机上出了问题：系统光标靠在屏幕上反色来闪烁，而 balloonui
是先画进后台缓冲、再整块拷上屏，两者相互干扰，光标会一会儿只亮上半段、一会儿只亮
下半段（客户端资料窗「备注名」文本框，实测 8 次复现 4 次）。现在的做法：

- 看得见的光标由 `DuiRichEdit::PaintCaret` 画进后台缓冲（反色，外观与系统光标一致），
  闪烁由 `DuiTextHost` 用线程定时器控制，周期取 `GetCaretBlinkTime()`。
- 系统光标照常创建、照常跟随插入点，输入法候选窗与辅助工具的定位不受影响；但它用一张
  **全零的单色位图**创建，在屏幕上不留任何像素。只做到「宿主不调用 `ShowCaret`」是不够的：
  msftedit.dll 的导入表里直接有 `ShowCaret` / `HideCaret` / `CreateCaret`，实测获得焦点或
  打字后的第一次绘制若发生在宿主的 `BeginPaint` 期间，`EndPaint` 之后系统光标就处于显示
  状态，宿主拦不住。
- 引擎在 `TxDraw` 里会隐藏再显示一次光标。这对后台缓冲毫无意义，`DuiTextHost::BeginDraw`
  / `EndDraw` 把这一对请求吸收掉，否则每次绘制都会引发下一次绘制，光标也不再闪烁。
- 引擎在有选区时会改用一张全零的位图光标（8×20）让光标「存在但看不见」。控件画位图光标
  时按位图的形状反色，不能只取它的宽高画成实心块。

对应的单元测试是 `Tests/DuiRichEditCaretTests.cpp`（CT1～CT8）。

另一条情报：`TxCreateCaret` 的第一个参数**不一定是位图**。开启"逻辑光标"编辑样式后
它变成一组标志位（`TextServ.h:285-308`、`richedit.h:243`）。默认情况下引擎给的是
真位图句柄或空值，右到左文字和斜体光标会用到位图。`DuiCaret` 两种情况都要处理，
且**位图的所有权在引擎，我们不得销毁它**。

还有一条防错规则来自参考实现（`SRichEdit.cpp:336-340`）：显示光标前必须检查
"本控件当前是否处于界面激活状态"，否则引擎会因为别的原因（比如收到设文本、设选区的命令）
要求显示光标，导致一个没有焦点的输入框在闪光标。

### 10.2 输入法

balloonui 全库没有任何输入法代码。需要做三件事：

1. **宿主补消息路由**：输入法的五条消息（开始组字、组字中、结束组字、输入法字符、
   输入法通知）加上输入语言切换，都要送到焦点控件。做法已定：宿主消息映射里明确列出，
   汇入控件基类新增的一个通用接口。
2. **提供输入法上下文**：`TxImmGetContext` 返回宿主窗口的输入法上下文，
   `TxImmReleaseContext` 配对释放。需要链接输入法库。
3. **候选窗定位**：靠 10.1 的系统光标解决。

参考实现还做了两件值得抄的事：启动时调整语言选项，**关掉"按输入内容自动换字体"**
（`SRichEdit.cpp:641-644`），否则同一行里中英文字体会不一致；以及密码框获得焦点时
把输入法从宿主窗口摘掉、失焦时装回去（`:722-725`、`:739-742`）。

### 10.3 滚动条

用 balloonui 现成的滚动条控件，作为子控件持有，但**布局时把矩形摆在文本区之上**
而不是旁边，这样不占内容宽度。绘制时必须最后画。

**这里有一个必须处理的无限递归。** 据实证（参考实现 `SRichEdit.cpp:398-406`、`:779-802`），
引擎与宿主之间会形成双向环：

```
引擎要求设滚动位置 → 我们更新滚动条 → 滚动条回调通知 → 我们通知引擎滚动
      ↑                                                          ↓
      └──────────────────── 引擎又要求设滚动位置 ←────────────────┘
```

反方向（用户拖滚动条）同样成环。解法是一个"正在处理滚动"的标志位，
**而且必须在两个地方判**：引擎要求设位置时判一次，我们自己的滚动处理函数里判一次。
只判一处堵不住另一个方向。

## 11. 已知的坑与待验证事项

本节严格区分已验证与未验证：有出处或实测结果的结论列为「据实证」并附上出处，
尚未验证的列为「据推测」。

### 11.1 据实证（有出处）

- **接口规模**：`ITextHost` 39 个方法、`ITextServices` 18 个。
  出处 `TextServ.h:317-445`、`:176-283`。
- **单位混用真实存在**：取客户区矩形用像素、取内边距用 HIMETRIC，两方法相邻定义。
- **两个接口标识符没有导入库导出**，必须手工声明（参考实现 `SRichEdit.cpp:169-183`）。
- **光标参数不一定是位图**（`TextServ.h:285-308`、`richedit.h:243`）。
- **透明背景是正式支持的**（`TextServ.h:42-45`）。
- **拖放目标由引擎提供**（`TextServ.h:275`）。
- **滚动存在双向递归环**，需两处防重入（参考实现 `SRichEdit.cpp:398-406`、`:779-802`）。
- **滚动位置必须回读**，因为引擎按行边界对齐（参考实现 `SRichEdit.cpp:787-796`）。
- **★ 引擎报的滚动「最大值」是内容总高，不是最大有效滚动位置。**
  （2026-08-14 实测确认）
  实测数据：内容总高 140、可视区 54，让引擎自己滚到底之后停在 **86 = 140 − 54**。
  也就是说真正能滚到的最底部要用「最大值减去一屏」算 —— 滚到底时最后一屏正好
  填满可视区，末尾之后不该露出空白。
  这两个口径差着整整一个屏幕高度。把最大值原样当成最大位置交给滚动条控件，
  症状是**滑块拖不到底**：拖过头被引擎夹回来，回读同步之后滑块自己弹回中间某处。
  顺带一提，换算之后滑块比例也自动正确 —— 库内滚动条按 `一屏 /（范围 + 一屏）`
  计算滑块大小，代入换算后的值正好等于 `一屏 / 内容总高`。
- **balloonui 的绘制路径不设裁剪区**，控件必须自己裁。基类注释中"由宿主裁剪"一句
  与代码不符（`DuiControl.h:145` 对比 `DuiHost.cpp:327-377`、`DuiControl.cpp:213-231`）。
  裁剪必须用求交的接口，不能用替换语义的那个，否则会撤掉外层容器已设的裁剪。
- **balloonui 不需要做透明通道的备份恢复**。后台缓冲是 32 位位图但压缩方式为纯 RGB
  （`DuiHost.cpp:971`），上屏走逐字节复制（`DuiHost.cpp:375`），全库无分层窗口。
  那第四个字节没有消费者，引擎写字把它清零无害。**这一条与参考实现不同**——
  参考实现必须做备份恢复，因为它用分层窗口合成。
- **宿主不处理定时器消息**。类注释里声称处理了，消息映射表里没有，代码里也没有
  （`DuiHost.h:22` 对比 `DuiHost.h:60-85`）。
- **宿主没有通用的消息转发入口**，每条消息各有独立处理函数。
- **★ 宿主原先每次重画都把整棵控件树画一遍，丢掉了系统算好的脏区。**
  （2026-08-14 实测暴露，已修复）
  系统在开始绘制时会把合并好的待重画区域交给程序，算得很准（打一个字通常只有
  一行文字那么高）。但宿主取的是整个客户区，于是控件树里「子控件矩形与待重画
  区域是否相交」这个判断永远成立，**每个控件每次都要重画**。演示程序里量到的
  数字：一次按键触发的重画耗时 80 毫秒，其中 79 毫秒花在排在目标控件前面的
  那些控件上（四十来个页签、十几段说明文字），目标控件自己只要 1.3 毫秒。
  这个问题一直存在，只是以前没人碰到 —— 静态界面很少重画，偶尔全量一次
  察觉不到；而文本输入每敲一个键就要求重画一次，累积起来就是肉眼可见的迟钝。
  修法：取用系统给的待重画区域，并且**给内存设备上下文设一次裁剪**。
  裁剪那一步是正确性保障而非性能优化 —— 很多控件的绘制函数不看传进来的
  待重画区域，上来就把自己的整个矩形铺满；不加裁剪的话，一个大容器会把整片
  区域刷成背景色，而它那些不相交的子控件又不会重画，结果是脏区之外的内容
  被抹掉。另外缓冲区刚重建时内容是未初始化的随机像素，必须退回整块绘制。
  实测效果：一次按键从 80 毫秒降到 0.77 毫秒，且只重画真正变化的那一个控件。
- **★ 宿主窗口从来不主动索取 Win32 键盘焦点，纯 DUI 控件因此一个按键也收不到。**
  （2026-08-14 实机暴露，已修复）
  这是 balloonui 的一处基础设施空缺，不是本控件的问题。宿主通常是某个顶层窗口的
  **子窗口**，而 Windows 不会因为用户点击了子窗口就自动把键盘焦点交给它 —— 必须
  程序自己去要。库里此前没有任何代码这么做，于是字符与按键消息全都投递给了宿主的
  父窗口，被丢弃。
  之所以一直没暴露：库里能打字的控件此前**全部是寄宿真子窗口的**（单行编辑框，
  以及当时还在的真窗口富文本控件），它们在获得 DUI 焦点时会自己调系统接口把焦点
  交给自家子窗口。
  纯 DUI 控件这条路径从来没有被走过。
  修法：`DuiControl` 新增一个默认为假的虚函数，由需要键盘的控件声明；宿主在 DUI
  焦点变化时只对声明了的控件索取 Win32 焦点。这样寄宿子窗口的控件行为零变化 —— 无条件
  索取会有两处副作用：把寄宿控件已经交给子窗口的焦点抢回来，以及点按钮时让正在
  编辑的输入框收到失焦通知（业务常据此认为「编辑结束」）。
  **教训**：控件、引擎、消息转发三处单测全绿，实机上却一个字打不进去。这类
  「两段各自正常、接缝处断了」的问题，只有把真窗口、真宿主、真控件串起来的端到端
  用例才钉得住。相应用例已补（见 `DuiRichEditTests` 里的键盘链路两条）。
- **★ 引擎完全不需要任何窗口就能工作。**（2026-08-14 实测确认）
  不接控件、不建窗口，只把宿主实现交给系统的创建函数，引擎即可创建成功，并且能
  正常灌入文本、读回文本、按给定宽度排版、算出内容自然高度、执行只读等属性位。
  验证方式：`Tests/DuiTextHostTests.cpp` 的十三条用例全部不创建窗口、回调接口传空，
  全部通过。**这条是整个无窗口路线的地基**——它成立，所以文本读写、选区、格式、
  尺寸测量、查找、持久化等绝大部分行为都能写成纯单元测试，不必搭建真窗口。
- **★ 读回的文本末尾会多一个回车符。**（2026-08-14 实测确认）
  写进去 `hello richedit`，读回来是 `hello richedit\r`。这是引擎维护文档结尾标记的
  既定行为，不是缺陷。凡是把读回的文本与写入值直接比较的地方都要先去掉尾部换行，
  否则会得到"内容不匹配"，而实际内容是对的。库内的富文本测试统一做了这个处理。
- **★ 「这个按键我用不上」的返回值是状态相关的。**（2026-08-14 实测确认）
  头文件里那个名为"按键被忽略"的返回值，表达的**不是**"这类按键不归我管"，
  而是"**在当前状态下**我用不上它"。实测数据（文档内容为三个字符、光标在开头）：
  Esc、Tab、F1、回车都报告为已消费；左方向键、上翻页报告为用不上——因为光标
  已经在开头、文档也只有一行，它们无处可去。把光标移到文档中间再按左方向键，
  同一个键就变成已消费。
  这恰好是冒泡最需要的语义：到边界了就把机会让给外层容器（例如外层列表接管
  方向键）。因此转发时应当照实读这个返回值，不能一律返回"已消费"——一律返回
  的话外层将再也收不到任何键盘事件，而且不报错、不崩溃，极难发现。
  顺带一提：Esc 被引擎声称消费，看起来会挡住"按 Esc 关对话框"，但在 balloonui
  里没有实际影响——宿主的按键处理本来就不看控件的返回值。
- **★ 测量内容自然尺寸的参数组合有两处必须给对。**（2026-08-14 实测确认）
  ① **范围参数必须传真实值**——传全零时，出参的宽和高会一并被写成 0，什么也量不到，
  而返回码是成功，不会提示哪里错了。② **目标设备上下文必须传空**——传一个屏幕设备
  上下文进去，调用会直接返回失败。正确的组合是：绘制用的设备上下文传屏幕的、目标
  设备上下文传空、目标设备描述传空、范围参数传宿主算好的那份（单位是百分之毫米）、
  宽度作为入参给出可用宽度、高度作为出参接收结果。参考实现完全没用过这个方法，
  没有先例可抄，这三条是实测出来的。

- **★ 引擎保存宿主指针时不增加引用计数，不存在引用环。**（2026-08-15 实测确认）
  写作时这一条只是从参考实现的释放链条反推出来的推测。验证方式是给宿主类加一个
  存活实例计数，构造再销毁控件之后计数应当回到基准值 —— 单个与批量各验一遍。
  用例 `DuiRichEditTests / NoReferenceCycleWithEngine`。
  之所以值得专门验：如果引擎那侧增加了引用计数，两者会互相拖住谁也释放不掉，
  那是一种不报错、不崩溃的内存泄漏，光看代码看不出来。
- **★ 库内的绘制目标本来就处于兼容图形模式，绘制前后那次模式切换是防御性的。**
  （2026-08-15 实测确认）
  参考实现必须切换（`SRichEdit.cpp:681`、`:704`），因为它的绘制目标设成了高级模式
  以支持世界变换；balloonui 没有用世界变换。实现里仍然保留了「切过去再切回来」的
  写法，因为它无论如何都安全、成本可以忽略；用例
  `DuiRichEditTests / BackBufferDcIsCompatibleGraphicsMode` 记录「当前确实不需要」，
  将来若有人在库里引入世界变换，它会失败并提醒。
- **★ 自动增高不会自己发生，必须有人要求重新排版。**（2026-08-15 实现时发现）
  「按内容算高度」这一半和「让父容器重新排版」那一半是分开的，只写前者的症状是
  打字时控件纹丝不动 —— 父容器的排版只在窗口尺寸变化时才跑。触发点有三个，缺一
  不可：内容变化通知（用户编辑）、`SetText`（程序改内容，走不到内容变化通知）、
  以及布局末尾的自纠。
  请求重排**必须是异步的**（投递消息而不是当场排版）：内容变化通知是排版引擎在
  处理按键的中途回调上来的，当场重排会形成对引擎的重入调用。
  还要防死循环：父容器完全可以不采纳报上去的期望高度（典型是布局提示写成了固定
  高度，而自动增高又默认打开），那时每排一次版控件都会发现高度不等，无条件再请求
  就会无限打转。实现里记住上一次请求的宽高来掐断。
- **★ 布局第一趟问期望尺寸时控件还没有宽度，量不出高度。**（2026-08-15 实现时发现）
  父容器的排版分两趟：第一趟问每个子控件想要多大，第二趟才把矩形分下去。第一趟
  发生时本控件的矩形还是上一轮的旧值，界面刚建出来那次更是全零。而富文本的高度是
  **按宽度算出来的**（同样的文字，框窄了就要多折几行、也就更高），宽度未知时根本
  量不出高度，只能报 0。症状是首次显示时自动档的编辑器高度为零、界面上完全看不见。
  解法是在布局末尾回头再量一次并请求重排，代价是首次显示多排一次版。
- **★ 排版引擎会丢弃没有配套「按键按下」的回车字符。**（2026-08-15 实测确认）
  真实运行时回车总是先来一条按键按下、再来一条字符消息（系统的 TranslateMessage
  由前者生成后者）。只投递字符消息的话，普通文字进得去、换行进不去，表现为「打了
  几个字，行数一直是一行」。写自动化测试模拟键盘输入时尤其容易踩。

### 11.3 已知问题

- **内容高度的测量结果偏小，且同样的行数会给出相差数倍的值。**（2026-08-14 发现，
  2026-10-09 复核：用 `SetText` 写入的情形已不复现；逐字键入的情形尚未复核）
  - 当时的现象：同一个控件（文本区 390×14）里，`SetText("line one\r\nline two\r\nline three")`
    量出 42 像素，而逐字键入的三段 `a / b / c`、以及随后 `SetText("a\r\nb\r\nc")` 都只量出

  - 影响：自动增高按这个高度决定控件长多高，量小了内容会被截掉一截。当时界面上看不出来，

  - 2026-10-09 复核：仍是 390×14 的文本区，依次 `SetText` 上述三段内容、`"aaa"`、

    一行 20 像素、三行 60 像素，三段内容不论长短都是 60 像素。逐字键入（模拟按键输入）
    的情形这次没有复核，状态仍算未确认。
  - 排查时可设环境变量 `BUI_DUI_TRACE=1` 打开测量函数里的埋点，它会输出调用返回值、

## 13. 无窗口路线解决了真子窗口方案的哪些问题

真窗口富文本控件已经删除，富文本只剩 `DuiRichEdit` 一个，因此这里不再有选型问题。
保留这一节是为了记住当初另起一个无窗口控件的理由 —— 它同时也是一份「哪些能力依赖
无窗口实现」的清单，将来若有人提议退回真子窗口，可以照着逐条核对代价。

| 真子窗口方案的限制 | 无窗口方案怎么解决 |
| --- | --- |
| 子窗口永远画在 DUI 合成层之上，既盖不住别的控件、也不会被别的控件盖住，因此进不了滚动容器、页签、弹出层 | 控件是 DUI 树里的普通一员，绘制次序与遮挡关系跟其它控件完全一致 |
| 背景由子窗口自己擦，做不出圆角、半透明、渐变，也跟不上布局动画 | 引擎正式支持透明背景（第 7 节），背景由控件在调 `TxDraw` 之前自行绘制 |
| 拿不到引擎内部的排版结果，高度只能由调用方写死 | `TxGetNaturalSize` 能算出内容的自然高度，接进布局体系即得到随内容自动增高（第 9.1 节） |
| 每个实例占用一个窗口句柄，一个窗口里放不了太多个 | 不创建任何窗口，实例数量不受句柄数限制 |
| 多行 / 只读 / 自动换行等属性编码在窗口风格位里，改一次要销毁重建 | 这些属性变成属性位，运行期随时可改，改完通知引擎一次即可（第 6 节） |

代价也一并记在这里，免得日后只记得好处：光标、输入法上下文、滚动条这三样在真窗口
模式下由系统包办，无窗口模式下必须自己实现（第 10 节）；引擎的回调顺序、坐标系与
单位混用也都成了本控件自己的负担（第 5 节）。内嵌图片与内容枚举正是因为这些额外
工作量，才在第一版里被推后（第 12 节第 7 条）。
